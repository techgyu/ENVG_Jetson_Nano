# 2025-09-30 | Reason why bufsize 20480 is appropriate for Lepton 3.5

---

Lepton 3.5 기준: 20480 바이트 버퍼가 적합한 이유
## 1. 프레임 크기 대비 충분한 여유
모드	패킷 길이	프레임당 패킷 수	계산된 프레임 크기
Raw14	164 바이트	60개	164 × 60 = 9,840 바이트
RGB888	244 바이트	60개	244 × 60 = 14,640 바이트

→ RGB888 모드에서 한 프레임을 온전히 저장하려면 최소 14,640 바이트 필요
→ 20480 바이트면 한 프레임을 저장하고도 5,840 바이트 여유 공간 확보

즉, 한 프레임 수집에는 충분하고 남는 공간도 있음

## 2. 버퍼 여유로 향후 확장 또는 안전성 확보 가능

Raw14 모드에서는 두 프레임 가까이 저장 가능 (9,840 × 2 = 19,680 바이트)
→ 일부 여유 바이트(800바이트 정도)도 남음

따라서, 모드 전환이나 프레임 경계 처리 오버헤드 등을 감안해도 버퍼 오버플로우 위험이 낮음

## 3. 재동기화 / 모드 변경 대응력 확보

Lepton 모드는 모드 변경 시 VoSPI 재동기화가 필요하다

데이터 읽는 중에 버퍼가 가득 차면 읽기 지연이나 데이터 손실 위험

20480이면 충분한 여유 공간 덕분에 모드 전환 타이밍(읽기-쓰기 엇갈림 등)에서도 버퍼 오버런 가능성 낮음

## 4. 메모리 사용 부담 적당

Lepton 3.5 수준의 영상 인터페이스에서는 수십 KB 정도의 SRAM이나 버퍼 공간을 확보할 수 있음

20,480 바이트는 몇 만 바이트 수준이므로 대부분의 임베디드 시스템에서도 감당 가능한 수준

반대로 아주 큰 버퍼 잡으면 MCU 메모리 자원 낭비 또는 다른 기능 영향 우려됨.

## 5. 복수 프레임 처리 또는 더블버퍼링 제외 시 적절한 타협점

만약 더블버퍼링을 원하면 2프레임 이상 저장 가능한 버퍼가 필요 → RGB888 기준 14,640 × 2 = 29,280 바이트 필요

하지만 시스템 자원 제약이 있다면, 20480 바이트는 단일 프레임 안정성 + 어느 정도 여유 확보라는 중간 타협점으로 실용적

즉 “모드 변경 + 프레임 처리 여유” 용도로 대부분의 상황에서는 충분한 안전 마진 제공

## 6. 요약

RGB888 모드 한 프레임을 저장하려면 최소 14,640 바이트 필요

20,480 바이트면 한 프레임을 완전히 담고도 여유 공간 확보

Raw14에서는 거의 두 프레임을 담을 수 있음

모드 전환이나 재동기화 상황에서도 버퍼 오버런 위험을 낮출 여유 있음

MCU / 임베디드 시스템 자원 대비 적절한 절충안
